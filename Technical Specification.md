# Техническое задание: Kaspi Statement Parser

## 1. Цель проекта

Автоматизировать разбор PDF-выписок из Kaspi Bank и превратить сырые транзакции
в понятную категоризированную аналитику личных расходов.

**Личная цель:** раз в месяц загружать PDF-выписку **с телефона через браузер**
и за 30 секунд видеть, куда ушли деньги — без ручного разбора выписки в Excel.
Приложение должно быть задеплоено и доступно из интернета, не только локально.

**Карьерная цель:** проект в портфолио, демонстрирующий уровень Middle Java
Developer / Java Middle SWE — production-подход, а не учебный CRUD-скрипт.

**Метрика успеха:** после загрузки выписки пользователь за 30 секунд понимает
структуру трат за месяц по категориям, вместо 20+ минут ручного разбора.

---

## 2. Функциональные требования

### MVP (первая итерация — обязательно)
- [ ] Загрузка одного PDF-файла выписки Kaspi
- [ ] Извлечение транзакций из PDF: дата, мерчант, сумма, тип (списание/пополнение)
- [ ] Справочник "мерчант → категория" (стартовый список 20–30 частых мерчантов)
- [ ] Категоризация транзакций через fuzzy matching по справочнику
- [ ] Сохранение выписки и транзакций в PostgreSQL
- [ ] Защита от дублирования при повторной загрузке одной и той же выписки
- [ ] Простой вывод результата: список транзакций + суммы по категориям за месяц
  (REST API, отдающий JSON)
- [ ] **Минимальный веб-интерфейс** (Thymeleaf или простой HTML+CSS+JS):
      страница с формой загрузки PDF-файла + отображение результата
      (категории и суммы). Адаптивная вёрстка под мобильный экран —
      основной сценарий использования это загрузка с телефона
- [ ] **Деплой на бесплатный хостинг**, чтобы приложение было доступно из
      интернета (не только в локальной сети) — кандидаты: Railway, Render,
      Fly.io. Учесть ограничения free-tier (sleep после простоя, лимиты по
      памяти/времени работы БД)
- [ ] **Базовая аутентификация** (Spring Security, один пользователь — сам
      Султан), т.к. это личные финансовые данные и приложение публично
      доступно из интернета

### Вторая итерация (после MVP)
- [ ] AI-fallback: если fuzzy matching не нашёл категорию — запрос к LLM
      (Gemini API free tier или локальная модель через Ollama, интеграция
      через Spring AI). Результат сохраняется в справочник, чтобы повторно
      к LLM не обращаться.
- [ ] Сравнение расходов месяц к месяцу, тренды
- [ ] Веб-дашборд с графиками (вместо чистого JSON-ответа)
- [ ] Массовая загрузка нескольких выписок сразу

### Явно вне scope (не делаем)
- Kafka / RabbitMQ / Redis — нет архитектурного сценария, который их оправдывает
  для однопользовательского личного проекта
- Мобильное приложение
- Интеграция напрямую с Kaspi API (не публичный, только парсинг PDF-выгрузки)

---

## 3. Модель данных (укрупнённо)

- **Statement** — загруженная выписка (файл-источник, период, дата загрузки)
- **Transaction** — одна операция (дата, мерчант как есть из PDF, сумма, тип,
  ссылка на Statement, ссылка на Category)
- **Category** — категория трат (Продукты, Транспорт, Связь, Развлечения и т.д.)
- **MerchantCategoryMapping** — справочник соответствий "название мерчанта →
  категория", пополняется вручную и через AI-fallback

---

## 4. Архитектурные решения

- Загрузка PDF — через REST endpoint (multipart upload), не сканирование папки
- Оригинальный PDF не хранится после парсинга (только извлечённые данные) —
  пересмотреть при необходимости аудита
- Транзакция без найденной категории помечается статусом "Без категории" и
  видна отдельным списком, не блокирует обработку остальной выписки
- Категоризация — сначала fuzzy matching (Apache Commons Text), LLM — только
  как fallback для несопоставленных мерчантов

## 5. Технический стек

| Категория | Технология |
|---|---|
| Язык | Java 17/21 (LTS) |
| Framework | Spring Boot 3.x (Web, Data JPA, Validation) |
| БД | PostgreSQL + Flyway (миграции схемы, без `ddl-auto=update`) |
| PDF-парсинг | Apache PDFBox (+ Tabula-java при необходимости) |
| Fuzzy matching | Apache Commons Text (Levenshtein / Jaro-Winkler) |
| Web UI | Thymeleaf (адаптивная вёрстка под мобильный экран) |
| Аутентификация | Spring Security (один пользователь) |
| Деплой | Railway / Render / Fly.io (free tier) |
| AI-интеграция (2 итерация) | Spring AI + Gemini API (free tier) или Ollama |
| Тесты | JUnit 5, Mockito, Testcontainers (PostgreSQL), AssertJ |
| API-документация | springdoc-openapi (Swagger UI) |
| Контейнеризация | Docker + Docker Compose (app + PostgreSQL) |
| CI | GitHub Actions (тесты + сборка на push) |
| Сборка | Maven |
| Логирование | SLF4J + Logback |

## 6. Milestones (порядок разработки)

1. Скелет проекта: Spring Boot + PostgreSQL подключение, Flyway baseline
2. PDF → сырой текст (PDFBox), без структурирования — только вывод в лог
3. Сырой текст → список структурированных `Transaction` объектов (regex/паттерны)
4. Сохранение Statement + Transaction в БД, защита от дублей
5. Справочник категорий + fuzzy matching категоризация
6. REST API: загрузка выписки, получение списка транзакций и агрегатов по категориям
7. Минимальный веб-интерфейс (Thymeleaf): форма загрузки PDF + отображение
   результата, адаптивная вёрстка под мобильный экран
8. Базовая аутентификация (Spring Security, один пользователь)
9. Тесты: unit на парсер и матчинг, integration через Testcontainers
10. Docker Compose, README, GitHub Actions CI
11. Деплой на бесплатный хостинг (Railway/Render/Fly.io), проверка доступа
    с телефона через интернет
12. (Итерация 2) Spring AI + LLM fallback для несопоставленных мерчантов
13. (Итерация 2) Графики, тренды месяц к месяцу, более развитый дашборд

## 7. Открытые вопросы / нужно исследовать

- Насколько стабилен формат PDF-выписки Kaspi между месяцами — требуется
  открыть реальный файл через PDFBox и посмотреть на сырой текстовый вывод
  до проектирования финального regex-парсера
- Многострочные транзакции (если описание мерчанта переносится) — уточнить
  на реальных данных
